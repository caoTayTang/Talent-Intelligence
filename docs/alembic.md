# Alembic Notes

Alembic is the database migration tool for SQLAlchemy. SQLAlchemy models describe what the database should look like in Python, and Alembic records how to change the real database schema over time.

In this project, Alembic replaces `Base.metadata.create_all()` as the real migration path. `create_all()` is okay for a quick scaffold, but it does not safely alter existing tables, track schema history, or support production deployment well.

## Mental Model

```txt
SQLAlchemy models -> desired schema
Alembic migration files -> step-by-step schema changes
Postgres database -> actual schema
alembic_version table -> current migration revision applied to the DB
```

A migration file is a Python file with two important functions:

```python
def upgrade() -> None:
    # apply schema changes

def downgrade() -> None:
    # undo schema changes
```

## Important Commands

Run commands from `apps/api` with the Python virtualenv active.

Check current database revision:

```bash
alembic current
```

Check latest migration revision in the repo:

```bash
alembic heads
```

Create a migration from model changes:

```bash
alembic revision --autogenerate -m "add document chunks"
```

Always open the generated migration and review it before applying it. Autogenerate is helpful, but not perfect.

Apply migrations:

```bash
alembic upgrade head
```

Mark the database as being at a revision without running schema changes:

```bash
alembic stamp head
```

Use `stamp` carefully. It is useful when the database already has the schema and you only need Alembic to start tracking it. It should not be used to skip real schema changes.

## Online vs Offline Migrations

Alembic has two execution modes.

Online mode connects to the database and runs the migration directly. This is the normal mode for local development and deployment.

```bash
alembic upgrade head
```

In online mode, `migrations/env.py` creates a SQLAlchemy engine, connects to Postgres, and executes migration commands against the real database.

Offline mode does not connect to the database. It renders SQL text instead. This can be useful if a DBA or deployment system wants to review or run SQL manually.

Example:

```bash
alembic upgrade head --sql
```

In offline mode, Alembic needs only the database URL/dialect so it knows how to generate PostgreSQL-compatible SQL.

## Project Setup

This project loads the database URL from the shared backend package:

```python
from talent_core.config import settings
```

The important value is:

```python
settings.sqlalchemy_database_url
```

That keeps API, worker, and migration code using the same `.env` database config.

## pgvector Notes

The `document_chunks` migration enables pgvector with:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

The embedding column uses a fixed dimension:

```python
Vector(2048)
```

This matches the current NVIDIA Llama Nemotron Embed VL 1B v2 model, which outputs 2048-dimensional embeddings. If the embedding model changes, the vector dimension must be reviewed before storing real vectors.

## Good Practice

- Do not edit old migrations after they are shared or deployed. Create a new migration instead.
- Review autogenerated migrations before running them.
- Keep schema changes in Alembic, not ad hoc SQL scripts.
- Run migrations before starting API/worker services in deployment.
- Do not use `create_all()` as the production migration system.
